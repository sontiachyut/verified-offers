## Real dependency evidence: SearchPagesIT

- Six tied-score offers paginate in deterministic identity order. Open the PIT,
  update one offer, delete another, insert an earlier-sorting identity, refresh,
  and replace the live alias. Continuing still returns the original frozen
  candidates without duplicates, omissions or the new identity. Another tenant
  retrieves none. Explicit PIT deletion makes subsequent use fail.
- With PostgreSQL verification enabled, eight offers begin as eligible. After
  the first page, price/version changes and a tombstone invalidate two upcoming
  candidates. Following alias replacement, later pages exclude those stale
  candidates but return every unchanged eligible identity in the original order.
- Pause the actual OpenSearch container during continuation: return 503, not
  stale data or an empty success. Resume the same cursor after recovery; a new
  earlier-sorting offer is still absent, proving the PIT was not silently reopened.
- Packaged API JVMs exercise GET continuation, scope/limit rejection, DELETE
  cancellation and subsequent 410. Restart the API and the previous process's
  cursor returns 410; an intentional fresh search succeeds.

The alias tests exercise the actual atomic OpenSearch handoff helper, not a full
Kafka coordinator run in each test. The ten existing OnlineRebuildIT tests still
cover that separate coordinator/replay acceptance gate.

## Unit evidence: SearchPagesTest

- Prefetched offers beyond the last examined hit are preserved for following
  pages. A source update between pages fails authoritative rechecking.
- Empty verified pages still advance. A 10,001-candidate fixture stops after
  exactly 10,000 examinations and exposes scanLimitReached without a cursor.
- Tenant/query/limit mismatch, signature modification and oversized tokens fail
  before index reads. Successful continuation does not extend expiry; exact
  two-minute equality returns 410.
- 128 failed opens exhaust admission without an unbounded retry leak. After
  the expiry/grace period, admission resumes. Failed closes and completed
  searches also retain their reservation until that fixed boundary.
- A transient continuation failure retains the same PIT for retry. Cancellation
  invalidates old cursors. A failed first page releases its known PIT, and a new
  process-local service rejects the previous service's cursor.

## Claims and remaining limits

This closes the local P3 functional search/pagination gate, not production
readiness. Ordering is snapshot-stable; source eligibility is current as of
each verification and can change on retries. No exact total, durable/HA cursor
state, auth-derived tenant isolation, multi-node failover or throughput result
is established. The eight-request admission semaphore is implemented; this
record does not claim a load/concurrency benchmark.

Cursor/PIT lifetime is fixed at two minutes. Abandoned contexts expire; early
deletion is best effort. Process-local reservations remain for an additional
ten seconds even after completion to bound uncertain network acknowledgements.
This intentionally caps fresh-search churn rather than promising 100 requests/s.

Index-quarantine replay/retention, authenticated tenancy, image remediation,
backup/restore and representative load experiments remain open operational
gates. Merchant feed jobs and an investigation UI are P4 work, not implemented
by this slice. See [ADR 0007](../adr/0007-stable-search-pages.md) and the
[pagination guide](../PAGINATION.md).
